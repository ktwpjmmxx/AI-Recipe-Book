# フェーズ3実験レポート：LLM-as-a-judge によるプロンプト設計の定量評価

**ステータス: ✅ 完了（8カテゴリ全て実行完了）**

対象プロジェクト: AI-Recipe-Book（`ai-assist` / `search-assist` 機能）
評価対象モデル: Gemini（`gemini-3.5-flash`, 2026年7月〜8月時点のスナップショット）

---

## 1. 背景・動機

AI-Recipe-Book には、登録レシピをベクトル検索（ChromaDB + Gemini embedding）で取得し、LLM（Gemini）が検索結果をもとに自然文で回答する `search-assist` 機能がある。この機能の本番プロンプトは、実装当初から一度も定量的に検証されておらず、以下のような挙動上の疑問が未解決のまま残っていた。

- 検索結果に複数の類似レシピが含まれる場合、1件に絞り込みすぎていないか、あるいは無関係なノイズまで回答に混ぜていないか
- 質問が曖昧なとき、断定的に1つの答えを返してしまっていないか
- データベースに存在しない情報（カロリー等）を尋ねられたとき、捏造していないか

これらは主観的な「使ってみた印象」でしか判断できておらず、AIエンジニアとしての学習ロードマップにおける「LLM評価・比較設計（LLM-as-a-judge）」フェーズの実践課題として、これらの疑問を定量的に検証することにした。

### 前提として明確にしておきたいこと

一般的な料理の作り方を尋ねるだけであれば、Gemini や ChatGPT に直接質問した方が、本アプリより遥かに広範なレシピ知識を持っている。したがって本実験、および `search-assist` 機能自体の価値は「レシピを検索できること」ではない。価値があるのは、**LLMが学習していない個人所有のデータ（登録レシピ）に対して、RAGを実装し、その出力品質を検証・改善するプロセスそのもの**である。実務における「社内文書に対するQA」「自社ECサイトの商品データ検索」等の縮図として、本プロジェクトを位置づけている。

---

## 2. 仮説

> プロンプトの指示内容を変えることで、同一モデル・同一検索結果に対する回答品質は変化する。ただし「常にどちらか一方が優れている」のではなく、**質問の状況（検索結果の件数・スコアの拮抗度合い・質問の意図）によって最適なプロンプトは異なるのではないか。**

この仮説を検証するため、以下の2種類のプロンプトを比較した。

| | 内容 |
|---|---|
| **プロンプトA（現行/シンプル版）** | 本番の`search_assist`で従来使用していたプロンプト。検索結果を提示し、レシピ名で言及するよう指示するのみ |
| **プロンプトB（改善案）** | プロンプトAに加え、以下4つの指示を追加：①関連度の低いノイズを無視する、②複数候補は区別して提示する、③曖昧な質問には確認を促す、④DBにない情報は断定しない |

## 3. 実験設計

### 3.1 テストデータセット

検証用に、既存の7件（豚の角煮・キーマカレー・ナシゴレン・ボンゴレビアンコ・ガスパチョ・鍋焼きうどん・ガトーショコラ）に加え、以下5件を意図的に追加し、計12件とした。

- バターチキンカレー、グリーンカレー（→ キーマカレーと合わせてカレー3件のクラスタを形成）
- 味噌汁、コーンスープ（→ 汁物ジャンルを拡充）
- ティラミス（→ ガトーショコラと合わせて洋菓子2件のクラスタを形成）

これにより、単一クラスタ内で意味的に拮抗する検索結果を意図的に発生させ、「複数候補が近い距離で同時にヒットする」状況を再現性を持って作り出した。

### 3.2 テストクエリ（8カテゴリ）

ChromaDBへの実際のクエリ実行結果（類似度スコア）をもとに、以下8パターンを最終確定した。

| カテゴリ | クエリ | ヒット件数 | 特徴 |
|---|---|---|---|
| 1件相当（大差・ノイズ混入） | 鍋焼きうどんの作り方を教えて | 2 | 本命と次点のスコア差が大きい |
| 1件相当（大差・名指し型） | キーマカレーの作り方を教えて | 3 | 類似ジャンル(他のカレー)がノイズとして混入 |
| 僅差の2件拮抗 | デザートが食べたい | 2 | スコア差ほぼ0（0.005） |
| 複数候補・属性検索 | カレーの作り方を教えて | 4 | 本命3件+ノイズ1件、かつ明確な手順要求 |
| 複数候補・ジャンル横断 | スープが飲みたい | 4 | 和洋を跨ぐ複数候補 |
| 曖昧・情報不足 | さっぱりしたもの食べたい | 4 | 料理名の指定なし |
| 制約付き（フォーマット遵守） | キーマカレーの材料を箇条書きで、手順は3行以内でまとめて | 3 | 出力形式の指定あり |
| 範囲外情報（DBにない情報） | キーマカレーのカロリーを教えて | 2 | DBに存在しない情報を要求 |

なお、検索結果が0件のケース（例:「餃子の作り方を教えて」）は、`search_assist`の実装上そもそもLLMを呼び出さず固定文言を返す設計になっているため、**プロンプト比較の対象から除外**した（比較不能なケースであるため）。

### 3.3 評価軸とjudgeの設計

以下5軸（各1〜5点）でGeminiに採点させ、勝者（A/B/tie）と理由を出力させた。

1. 関連性（relevance）
2. 忠実性（faithfulness）
3. 網羅性（completeness）
4. フォーマット遵守（format_compliance）
5. 有用性（usefulness）

バイアス対策として、A/Bの提示順は毎回ランダム化し、judge自身にはどちらがA・Bかを伏せた上で判定させ、結果をコード側で正しいラベルにマッピングし直した。

### 3.4 実験のスコープと既知の限界

- 本実験は商用LLM API（Gemini）を対象としているため、生成時は`temperature=0.2`、judge時は`temperature=0.1`に固定し、出力のブレを抑制した。ただし各カテゴリ1試行のみであり、複数回試行による統計的な多数決までは無料枠の制約上実施していない。
- 基盤モデルは提供企業側の裁量で更新・非推奨化されうる（本プロジェクトでも実際に`gemini-2.0-flash`の廃止を経験している）。したがって本評価結果は「gemini-3.5-flash（2026年7〜8月時点）における一時点のスナップショット」であり、恒久的な結論ではない。モデル更新時に低コストで再実行可能な回帰評価ハーネスとして評価スクリプトを設計した。

## 4. 実装上の技術的課題と対応

実験を実行する過程で、いくつかの想定外の技術的問題に直面し、その都度対応した。副産物として得られた学びも含めて記録する。

### 4.1 レシピがUIに1件も表示されない不具合

実験用データを追加した後、UIでレシピ一覧が0件になる不具合が発生した。調査の結果、**DB内の全12件のレシピの`user_id`が`None`のまま登録されており**、`/api/recipes`エンドポイントが現在ログイン中のユーザーIDでフィルタしていたことが原因と判明。全レシピの`user_id`を現在のログインユーザーIDに一括更新して解消した。

### 4.2 フロントエンドのタイムアウト

ハイブリッドロジック導入後、複数候補が拮抗するケースでは「意図判定→回答生成」の2回のGemini呼び出しが発生し、処理時間が約30秒に達するようになった。フロントエンドのaxiosタイムアウトがデフォルト30秒だったため、処理は正常に完了しているにもかかわらず画面に何も表示されない事象が発生。`search-assist`呼び出しのタイムアウトを60秒に個別延長して解消した。

### 4.3 無料枠の制約（1日20リクエスト）

`gemini-3.5-flash`の無料枠は「1分あたり」ではなく**「1日あたり20リクエスト」**という上限があることが実行中に判明した。これに対応するため、評価スクリプトに以下を実装した。

- 日次上限エラーを検知した場合は待機せず即座に処理を中断する（`PerDay`エラーはリトライしても回復しないため）
- コマンドライン引数でカテゴリ番号を指定し、複数日に分けて実行できる仕組み
- 実行結果を逐次JSONファイルに保存し、既存の完了済みカテゴリは自動スキップする仕組み

### 4.4 judgeのJSON出力パース失敗

`response_mime_type="application/json"`を指定していても、まれに応答の前後に余分な文字列が付与されJSONパースに失敗するケースがあった。最初のバランスの取れた`{...}`ブロックのみを抽出する堅牢なパーサーを実装し、それでも失敗する場合は1回だけ再生成を試みる仕組みで対応した。

## 5. 結果①：プロンプトA単体 vs プロンプトB単体（8/8完了）

| カテゴリ | 勝者 | 判定理由の要旨 |
|---|---|---|
| 1件相当・ノイズ混入 | A | Bの「登録情報にない旨の注記」が冗長で有用性を下げた |
| 1件相当・名指し型 | A | 同上。加えてBは材料の一部を1行にまとめ視認性が低下 |
| 僅差の2件拮抗 | B | Aが登録情報にない外部知識（「イタリアンデザート」等）を混入させた |
| 複数候補・属性検索 | A | Bが手順を省略し「どれが知りたいか」と聞き返すに留まり、実用性で劣った |
| 複数候補・ジャンル横断 | B | ジャンル別の整理・区別提示がBの得意分野として機能した |
| 曖昧・情報不足 | B | Aが独断で1つに絞り込んだのに対し、Bは複数の選択肢を提示できた |
| 制約付き（フォーマット遵守） | B | フォーマット遵守は互角以上にBが上回った |
| 範囲外情報 | tie | 「情報がない」と正直に言う基本動作は、Aの時点で既に十分にできていた |

**プロンプトA: 3勝　プロンプトB: 4勝　引き分け: 1**

### 得られた知見

- 検索結果の**本命が明確な場合（スコア差が大きい）**：プロンプトAのシンプルな指示で十分。Bの追加指示は冗長な注記を生み、かえって有用性を下げる
- **複数候補が拮抗する場合**：プロンプトBの「区別して提示する」「確認を促す」指示が有効に機能する
- ただし「複数候補・属性検索」（カレーの作り方を教えて）のように、**質問が明確に手順を求めている場合は、Bの「確認を促す」指示が過剰適用され逆効果**になることが判明した

この最後の知見が、後述するハイブリッド設計の核心的な着想になった。

## 6. ハイブリッドロジックの設計と実装

上記の知見をもとに、本番の`search_assist`を以下の2段階の分岐ロジックに変更した。

```
1. 検索結果が0件 → 従来通り固定文言を返す（LLM呼び出しなし）

2. 検索結果が1件のみ、または本命と次点のスコア差が0.08以上
   （実験データにおける「1件相当」ケース: 0.12〜0.16、
     「拮抗」ケース: 0.005〜0.03 の間に十分な余裕を持たせた閾値）
   → 判定コールなしでプロンプトA相当を使用

3. 上記以外（複数候補が拮抗している）
   → Geminiに1回だけ「質問が具体的な手順を求めているか(A)、
      提案・選択を求めているか(B)」を判定させ、
      結果に応じてプロンプトA/Bを選択する
      （判定に失敗した場合は、実害の小さいBにフォールバック）
```

実装は `backend/services/ai/gemini_client.py` の `search_assist` メソッド、および `_is_single_clear_result` / `_classify_intent` / `_build_prompt_a` / `_build_prompt_b` として反映した。

## 7. 結果②：ハイブリッド版 vs プロンプトA単体 vs プロンプトB単体（8/8完了）

3者の回答を1回のjudge呼び出しで比較する評価スクリプトを別途構築し、A・B単体の回答は既存の実行結果（結果①）を再利用（再生成せず）することでAPIコストを抑えた。

### 実行の途中経過：指示④の副作用の発見と修正

1回目の実行（6カテゴリ完了時点）で、意図判定が正しく機能した2つの重要なケースでハイブリッドが勝利し、設計の妥当性を確認した。

- 「複数候補・属性検索」（カレーの作り方を教えて）：誤ってBに倒れず、正しくA相当を選択し手順まで提示
- 「曖昧・情報不足」（さっぱりしたもの食べたい）：正しくB相当を選択し、複数候補の提示を実現

一方で、「僅差の2件拮抗」「複数候補・ジャンル横断」の2件では、**プロンプトBの指示④（DBにない情報は断定しない）が、質問が求めてもいないのに一律で発動し、judgeから「不要なメタ発言」として評価を下げられる**という共通の敗因が判明した。

これを受けて、指示④を「常に含む」設定から、**質問文に栄養関連キーワード（カロリー・栄養・成分・糖質・脂質等）が含まれる場合のみ動的に注入する**設計に修正した。

```python
_NUTRITION_KEYWORDS = ("カロリー", "栄養", "成分", "糖質", "脂質", "たんぱく質", "タンパク質", "kcal")

def _mentions_nutrition_info(self, question: str) -> bool:
    return any(keyword in question for keyword in self._NUTRITION_KEYWORDS)
```

### 最終結果（8/8）

| カテゴリ | ハイブリッドの分岐 | 勝者 | 補足 |
|---|---|---|---|
| 1件相当・ノイズ混入 | single_clear（プロンプトA相当） | hybrid | 同一プロンプトの生成ブレの範囲 |
| 1件相当・名指し型 | single_clear（プロンプトA相当） | prompt_A | 同上（マークダウン記法の僅差） |
| 僅差の2件拮抗 | ambiguous → B相当 | prompt_A | 僅差。修正後、hybrid自身のカロリー注記問題は解消（同じ問題が残っていたのは過去データのプロンプトB単体側のみ） |
| 複数候補・属性検索（手順要求） | ambiguous → **A相当** | prompt_A | 意図判定は正しくAを選択。hybridは調味料の分量補完がない点でわずかに劣る |
| 複数候補・ジャンル横断 | ambiguous → B相当 | **hybrid** | 温冷・和洋のジャンル対比を明確に整理できた |
| 曖昧・情報不足 | ambiguous → B相当 | **hybrid** | プロンプトA単体は断定的に1つに絞り込みcompleteness=2の大幅減点。hybridは自然な形で確認を促せた |
| 制約付き（フォーマット遵守） | single_clear（プロンプトA相当） | prompt_B | 唯一Bが勝利。3行への手順圧縮における工程選択の巧拙で、生成ブレの範囲内 |
| 範囲外情報（DBにない情報） | single_clear（プロンプトA相当） | **hybrid** | 材料の分量から一般的なカロリー目安を算出して提示するという、捏造ではない付加価値を発揮 |

**最終集計：ハイブリッド 4勝／プロンプトA単体 3勝／プロンプトB単体 1勝／引き分け 0**

### 結果からの考察

- 意図分類ロジックは8カテゴリを通じて**誤判定が一度も発生しなかった**（手順要求カテゴリでは常にA、提案・曖昧カテゴリでは常にBを選択）
- 指示④の条件付き化により、修正前に敗因となっていた「不要なカロリー注記」の問題は、hybrid側では完全に解消された（最終結果でこの問題が言及されたのは、旧仕様のまま再利用しているプロンプトB単体の回答に対してのみ）
- `single_clear`分岐（4カテゴリ）における hybrid と prompt_A の勝敗は、両者が全く同じプロンプトを使用しているため、**設計の優劣ではなく温度0.2でも残る生成レベルの偶発的なブレ**である。この4カテゴリを除いた「意図判定が実際に働いた4カテゴリ」に限れば、ハイブリッドは2勝2敗であり、うち2勝は本実験の核心的な仮説（状況に応じた動的なプロンプト切替の有効性）を直接裏付けるものである

## 8. まとめ

### わかったこと

- プロンプト設計に「絶対的な正解」は存在せず、検索結果の状態（件数・スコアの拮抗度合い）と質問の意図によって最適な指示内容は変化する
- この状況依存性は、単純な「A/Bどちらか一方を採用する」という結論ではなく、**条件に応じてプロンプトを動的に切り替えるハイブリッド設計**によって対応できる。実際、8カテゴリ中で意図判定が実際に働いた4カテゴリのうち2カテゴリで、ハイブリッドが単体プロンプトに対して明確な優位性を示した
- ハイブリッド設計自体にも副作用（指示の一律適用による過剰な注記等）が生じうる。今回はjudgeの評価理由を分析することでこの副作用を特定し、「常時適用」から「条件付き適用」へ修正することで解消できた。**LLM-as-a-judgeは単に勝敗を数えるだけでなく、reasoningを読み込むことで具体的な改善点を特定できる**という点が、この評価手法の実務的な価値である
- 商用LLM APIを用いた評価には、無料枠の制約・出力のランダム性・モデルの非推奨化など、ローカルモデルでは発生しない固有の制約が伴う。これらは検証を無意味にするものではなく、**低コストで再実行可能な評価ハーネスとして設計する**ことで対処すべき対象である

### 今後の展望

- 本実験で構築した評価ハーネス（`evaluate_prompt_variations.py` / `evaluate_hybrid_comparison.py`）は、今後モデルが更新された場合や、プロンプトをさらに改良した場合に低コストで再実行できる回帰評価として維持する
- 次の学習フェーズでは、レシピアプリという題材を介さず、簡易的なデータベースに対する検索精度そのものを検証する実験に取り組む予定（RAGの評価という関心の直接的な発展）
- GrepAI（学習記録リポジトリ）へ、本実験のプロセス全体を体系化して記録する

## 9. 再現方法

本実験で使用したスクリプトは以下の通り（`backend/`ディレクトリ直下で実行）。

| スクリプト | 役割 |
|---|---|
| `verify_test_queries.py` | テストクエリ8カテゴリの検索結果（ヒット件数・スコア）を検証するログを出力 |
| `evaluate_prompt_variations.py` | プロンプトA単体・B単体の8カテゴリ比較を実行 |
| `evaluate_hybrid_comparison.py` | ハイブリッド版・A単体・B単体の3者比較を実行 |

いずれも無料枠の日次上限に対応するため、コマンドライン引数でカテゴリ番号を指定した分割実行に対応している。

```bash
python evaluate_hybrid_comparison.py        # 全カテゴリ実行
python evaluate_hybrid_comparison.py 5 6 7 8  # 指定カテゴリのみ実行
```
